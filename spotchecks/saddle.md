## Other findings
- The source has no vendored MCP Adapter: `includes/lib/` is absent, and `includes/class-saddle-mcp.php:1030` says shipped zips do not include it. The built-in transport is the only path on a WordPress.org install. The adapter path is used only if the separate MCP Adapter plugin is active, and it still uses Saddle's `authenticated()` gate.
- Abilities are registered with `show_in_rest => true` (`includes/abilities/core-content.php:621`), so they can also be run through core's `wp-abilities/v1` with a cookie session or a hand-made Application Password. The same tier and capability closures still apply. Saddle-issued keys and bearer tokens cannot reach that route (`includes/class-saddle-connection.php:141`, `includes/oauth/class-saddle-oauth-bearer.php:85`).
- Integration-engine wrappers take their read-only/destructive status from the partner plugin's annotations. A read-only annotation lets a wrapper run at the Read only tier (`includes/class-saddle-integration-engine.php:341`). Wrappers are off until the owner enables them.
- The Unsplash Access Key, a third-party key rather than one the plugin issues, is stored in plain text and registered with `show_in_rest => true` for core's connectors screen (`includes/class-saddle-services-connector.php:57`). Only a 4-character hint is shown in Saddle's own UI (`includes/class-saddle-unsplash.php:97`). This is minor, and the key is not reachable through get-option.
